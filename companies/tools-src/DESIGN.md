### 案A: cite-gap（出典ギャップ検出）
- 名前: `cite-gap`（npm 404、PyPI 404 = 空き）。npmには別物の `citeguard` が存在（下の競合）。紛らわしいので README で違いを明記する。
- 何をするか: 文章中の「数字・統計・断定」を含む文で、同じ文または同じ段落に出典（URL、「出典」「取得日」）か「未確認」の印が無いものを列挙する。**真偽は判定しない**（出典があっても正しいとは限らない）。日本語と英語に対応。完全ローカル、外部通信なし。
- 入力例: Markdownファイル。
  `国内の副業人口は2割に達した。` / `調査では売上が3倍になった（出典: https://example.com/x 取得日2026-10-01）。`
- 出力例:
  ```
  draft.md:12  出典なし  「国内の副業人口は2割に達した。」  理由: 割合(2割)
  ```
  終了コードは、ギャップがあれば1、なければ0（CIや公開前フックに入れられる）。`--json` も用意。
- 想定ユーザー: AIで記事や資料の下書きを作る個人・ブロガー・学生。「AIが出した数字をそのまま出してしまう」失敗を防ぎたい人。
- 競合（WebSearch 1回、要約のみ・未確認多し）:
  - numaudit（PyPI）: 数字が「渡したデータファイル」に載っているかを見る。データ照合型で、出典の有無を見る当案と目的が違う
  - CiteGuard（npm）: 引用元を取得して主張を支持するか判定。LLMのキーと通信が要る。週DL 38（検索結果に表示された値、取得日2026-10-12、出典: https://socket.dev/npm/package/citeguard の検索要約）
  - sourceror（PyPI）: 学術引用をCrossRef等で検証。対象が別
  - efc / trustmebro: エージェント用の事実確認CLI、リンクの生死確認
  - 日本語の数字表現（「2割」「3倍」「約1,200円」）に特化したオフライン型は、検索範囲では見つからなかった（網羅していない）
- 作りやすさ: 高。Python標準ライブラリ（`re`, `argparse`）だけ。精度の限界（誤検出・見逃し）を README に明記。

### 案B: paste-check（AIに貼る前の漏洩点検）
- 名前: `pastecheck-ja`（npm 404、PyPI 404 = 空き）。`pasteguard` は別プロジェクトが既に存在（GitHub: sgasser/pasteguard、検索要約）。名前を避けた。
- 何をするか: テキストを外部AIに貼る前に、メールアドレス、電話番号、郵便番号、12桁の数字（マイナンバー形式の疑い）、クレジットカード番号らしい16桁（Luhn検査）、APIキーらしい文字列（`sk-`、`ghp_`、`AKIA` 等の接頭辞）を検出する。出力はマスク表示で、元の値は画面にも全部は出さない。
- 入力例: `連絡先は taro@example.com、090-0000-0000 です。`
- 出力例: `memo.txt:1  メールアドレス  ta***@example.com`、終了コード1。
- 想定ユーザー: 会話型AIに業務メモや議事録を貼る個人・小規模事業者。
- 競合（WebSearch 1回、要約のみ）: Shush（ファイルからPII・秘密を除去するCLI）、kloak（PyPI、Presidio基盤）、PasteGuard（ローカルプロキシ）、RedactCast（Raycast拡張）、各種Chrome拡張。**競合が最も多い案**。日本の番号形式への特化が差別化だが、効果は未検証。
- 作りやすさ: 高（正規表現とLuhn）。
- 懸念（採用しない理由）: 「検出されない=安全」と誤解されると、漏洩の事故に責任を負いかねない。氏名や店名は正規表現で拾えない。免責を強く書いても、**漏洩防止を名乗るツールの責任範囲は法的に未整理**（専門家確認が必要）。

### 案C: draft-gate（公開前の「残骸」点検）
- 名前: `draftgate`（npm 404、PyPI 404 = 空き）。
- 何をするか: AIの下書きを公開・送信する前に、**文体ではなく作業の残骸**を探す。
  - 未完了の印: `TODO`、`TBD`、`XXX`、`【要確認】`、`○○`、`[ここに…]`、`{{変数}}` の未置換、`lorem ipsum`、ダミー値
  - AIの返答の混入: 文頭の「承知しました」「以下に〜を示します」、`As an AI`
  - 構造: 閉じていないコードブロック、中身のない見出し、同一見出しの重複
  - 利用者定義: JSONファイルで独自の印を追加できる（例: 社内の確認待ち印）。本体に特定の組織名は入れない
  - 設定した「ゲート」（例: 公開前は `【要確認】` が0件であること）を満たさなければ終了コード1
- 入力例: `## 料金\n【要確認】月額は○○円です。\n以下に記事を示します。`
- 出力例:
  ```
  post.md:2  未完了の印  【要確認】
  post.md:2  プレースホルダ  ○○
  post.md:3  AI返答の混入  「以下に…示します」
  ```
- 想定ユーザー: AIで文書・記事・メールを作る個人。「確認待ちの印を残したまま公開した」事故を防ぎたい人。
- 競合（WebSearch 1回、要約のみ）: Prose Lint（AIの癖を指摘する文体リンタ）、slop-check、cw-ai-check（文体・残渣の監査スキル）、DraftCheck（ブラウザ型）。**残骸と確認待ち印に絞ったゲート型の既製ツールは、検索範囲では見つからなかった**（網羅していない）。textlint との重複: `preset-ai-writing` は文体の癖、当案は作業の残骸と終了コードでのゲートで、役割が違う。
- 作りやすさ: 高。Node標準（`node:fs`, `node:test`）だけ。

## ② 推奨2本
| 順 | 案 | レジストリ | 理由 |
|---|---|---|---|
| 1 | A cite-gap | PyPI | 「AIの数字をそのまま出す」失敗はKeitaの一次情報に直結。日本語の数字表現に絞れば差別化できる（仮説）。真偽判定をしないので、責任範囲が狭い |
| 2 | C draft-gate | npm | 競合の空白が見える（検索範囲）。構造が単純で、1日で作れる。ゲートという考え方がサイトの軸（承認ゲート）と一致 |
| 保留 | B paste-check | — | 競合が最多で、漏洩防止の名乗りが責任問題になる。A/Cの結果を見て再検討 |

2本を別のレジストリに分けるのは、PyPIとnpmのどちらで反応が出やすいかも測るため。ただし1本ずつなので比較としては弱い（因果は言えない）。

## ③ 共通設計
- **構成**: 1ツール=1フォルダ（`companies/tools-src/cite-gap/` 等）。公開は**別の公開リポジトリ**に切り出す。このリポジトリ（`thinking-log/`、`inputs/` 等）は公開しない
- **README**: ①何をする/しない ②インストールと実行例（入出力つき）③限界（誤検出・見逃し）④免責 ⑤AI利用の明記 ⑥ライセンス ⑦連絡先はGitHub Issuesのみ
- **ライセンス**: MIT。`LICENSE` の著作権者名はペンネームにする（ペンネームでの権利表示の可否は**専門家確認が必要**）
- **免責（README冒頭近く）**: 「現状のまま提供。点検の補助で、正確性・法令適合・安全を保証しない。真偽や漏洩の有無の最終判断は人が行う」。法的助言ではない
- **AI利用の明記**: 「設計・実装・テスト・READMEの下書きはAI（Claude）が行い、人が公開と最終確認をした」と事実を書く。隠さない。AI検出回避の機能は付けない
- **バージョン**: 0.1.0 から。SemVer。`CHANGELOG.md` を置く。1.0 は外部の利用が確認できてから
- **テスト**: Python は `unittest`、Node は `node:test`（どちらも標準）。入出力例を全てテストにする。AIが実装したので、**人が見るべき重要なテスト（誤検出の例）を先に決める**。公開前に、実行結果（件数）をREADMEに書く
- **依存・通信**: 外部依存ゼロ、ネットワーク通信なし（コードに通信モジュールを含めない。テストで確認）
- **データ**: 例文は全て架空（`example.com`、`090-0000-0000` 等）。実在の個人・企業・口コミは使わない
- **ペンネーム公開（作者名欄に本名・メールを入れない）**:
  - `pyproject.toml`: `authors` に名前だけ入れてメール欄は書かない。`project.urls` はGitHubのみ
  - `package.json`: `author` は `"ハンドル名"` のみ。`repository` はGitHub URL
  - Gitのコミット作者: 公開用リポジトリでは `user.name` にハンドル名、`user.email` にGitHubの非公開用noreplyアドレスを使う（GitHubの設定で用意。**画面の言葉は要確認**）。過去コミットに本名が混ざらないよう、公開用は**新規リポジトリで履歴を新しく始める**
  - 要確認: **npmは公開メタデータに公開者のメールが載ることがある**（記憶による。未確認）。また、PyPIのプロフィールでメールが他人に見えるかも**未確認**。公開前に、実在の別パッケージのJSON（`registry.npmjs.org/<名前>`）で、`_npmUser` にメールが出るかをCEO側で確認する。出るなら、本名と紐づかない専用の無料メールを使うかをKeitaが判断する
  - 完全な匿名性は保証されない。規約が実名を要求するか、ペンネーム運営の扱いは**未確認**（Keitaが各サービスの画面で確認）
